# Crossword Clash

## Project Overview

Real-time multiplayer crossword puzzle game. Supports solo play with localStorage persistence and competitive multiplayer via Supabase Realtime Broadcast channels.

## Stack

- **Frontend**: React 19 + TypeScript + Vite 7 + Tailwind CSS v4 + i18next/react-i18next
- **Backend**: Supabase (Postgres + Auth + Realtime Broadcast)
- **Testing**: Vitest
- **Package manager**: pnpm

## Commands

- `pnpm dev` — start dev server
- `pnpm build` — type-check + production build
- `pnpm preview` — preview production build
- `pnpm test` — run unit tests (vitest)
- `pnpm test:watch` — run tests in watch mode

## Architecture

- **State management**: Single `useReducer` in `src/hooks/usePuzzle.ts` — no external state library. Derived values (activeClue, highlightedCells) via `useMemo`.
- **Supabase client**: Nullable singleton in `src/lib/supabaseClient.ts` — app works fully offline when env vars aren't set (only "Play Solo" available).
- **Puzzle import**: `@xwordly/xword-parser` parses .puz/.ipuz/.jpz/.xd files, then `src/lib/puzzleNormalizer.ts` converts to internal `Puzzle` type.
- **Persistence**: Solo mode uses localStorage for puzzle + progress and **writes no server rows** — no `puzzles`, `games` or `players` insert on load and nothing mirrored per keystroke (the only server-side trace of a solo game is its `play_sessions` row; `GameContext.gameId` is null while solo). Multiplayer sessions (`crossword-clash-mp` / `crossword-clash-host`) are persisted to localStorage so players auto-rejoin on page refresh. Supabase handles multiplayer state via `claim_cell` RPC. **Puzzle rows are deduplicated by content**: `uploadPuzzle` (every hosting path — file, daily, classic, picker, deep link) looks the puzzle up by `puzzleContentHash()` (`src/lib/puzzleHash.ts`: SHA-256 of a canonical, key-sorted JSON of title, author, size, grid and clues), stored in the `file_hash` column, and inserts only when it is missing; a losing race on the column's unique constraint re-reads the winner's row.
- **Multiplayer**: Supabase Broadcast channels for real-time cell claims. Conflict resolution: local check → server `claim_cell` RPC with row lock → broadcast. No deletion in multiplayer — correct letters are permanent. Host can close the room via `room_closed` broadcast, which boots all players back to the menu. Players leaving intentionally broadcast `player_left` so others see them disappear immediately. **The live roster is Realtime presence** (`presenceStateToPlayers` in `useMultiplayer.ts`; the DB `players` rows are only the bootstrap while presence warms): each player `track()`s on every `SUBSCRIBED` (the server forgets a presence when the socket drops, and realtime-js does not replay it) and again on `visibilitychange` → visible, and untracks only on an intentional leave or `pagehide`, never on a hidden page — a locked phone, a notification or another tab used to untrack the host and empty everyone's lobby until the phone came back. **Room status and `hydrated` are keyed by the room id inside the hook** (`statusState`, `hydratedFor`): the hook lives in the app-wide `MultiplayerContext`, so after one game a new room's lobby used to read the previous game's `active` + hydrated on its first render and jump to `/play` ("Create room opened the puzzle"); the rest of the per-room state (roster, share code, clock, finish times, settings) is reset when the room id changes.
- **After the finish** (navigation audit §2–3, `docs/navigation-audit.md`): `CompletionModal` makes Share the one primary action ("Share your time" after a daily), then the daily board and the challenge link, then an **Up next** list (`nextUpSuggestions` in `src/lib/nextUp.ts`, gathered by `useNextUp`: today's unsolved dailies mini → midi → large, else one unplayed classic, else the library; a daily or classic loads straight into the solo screen, whose once-per-puzzle refs reset on puzzle identity) and a "Race a friend live" row; "Back to menu" is the quiet exit and the importer is never offered (the header keeps "Load different puzzle"). Fresh puzzles come from the **picker** (`/pick-puzzle?intent=race|next`, `PuzzlePickerScreen`): today's unsolved dailies plus the classic grid (`ClassicList`, shared with `/classics`). `race` tears the finished state down and hands the pick to the host flow as `urlPuzzle`; `next` (the multiplayer host's "Next puzzle, same room") uploads the pick and calls `createNextGame` with *its* id, so the room code stays and nobody rematches the solved grid — the TV view's "Next puzzle" goes through its own importer. **Daily board**: the finish is parked in `GameContext.pendingDailyResult` (`PendingDailyResult`: entry + the submission promise); `DailyLeaderboardScreen` awaits it before its first fetch, shows the viewer's own row at once (`mergeOwnResult`), refetches on `visibilitychange`, and once the viewer has solved the slot shows "Solved in 1:42 · #n today" and races a fresh puzzle through the picker instead of replaying it. `BoardSignForm` is the one "sign the board" form (modal + board).
- **Retention** (migration `20261023000000_retention.sql`, tested by `retentionMigration.test.ts`): nothing on the server lives forever. `retention_sweep()` (SECURITY DEFINER, revoked from anon/authenticated, every window a named constant in its DECLARE block) runs nightly at 04:17 UTC under pg_cron (`cron.schedule('retention-sweep', …)`; re-running the migration re-schedules it) and returns one row per step, so `select * from retention_sweep();` is also the manual run. Windows: `waiting` rooms untouched 12 h and `active` rooms untouched 24 h → `closed` (both past the 1 h / 12 h rejoin limits in `sessionPersistence.ts`, which the test holds them to); `closed`/`completed` games deleted after 90 days (players cascade, `daily_results.game_id` → null); `puzzles` with no game and older than a day deleted; anonymous `auth.users` older than 30 days with no refresh token in 30 days and no `players`/`play_sessions`/`daily_results`/`narrator_sessions`/hosted `games`/`entitlements` rows deleted (the sweep is redefined by the entitlements migration; the newest definition wins) (a returning device just signs in anonymously again); `narrator_usage` after 31 days (past the 30-day demo window); `play_sessions.clues` emptied after 180 days (the insights panel asks for at most 90) and rows deleted after 2 years. "Untouched" is `games.updated_at`, a trigger-maintained column this migration adds (claims, start, finish and close update the row; a lobby join does not). The same migration indexes `play_sessions (started_at)` for `insights_puzzles` and takes `games`/`players` out of the `supabase_realtime` publication (rooms use Broadcast; nothing subscribes to Postgres Changes). The privacy policy's "Retention and your choices" paragraph states these windows.
- **Capacitor plugin objects are Proxies that answer every property, `then` included**, with a native-method wrapper. So a promise must never resolve with a plugin object (`import("…").then((m) => m.Purchases)`, or `return m.SocialLogin` from an async function): JavaScript takes it for a thenable, calls a native "then" that never answers, and the promise hangs forever with no error anywhere (the 1.1.0 build 10 paywall froze on this). `nativePurchase.ts` and `nativeSignIn.ts` keep the module namespace in their promises and read the plugin off it synchronously; `nativePluginProxy.test.ts` loads both through a proxy with that property and fails if the pattern comes back.
- **App updates (the apps)**: `src/lib/appUpdate.ts` wraps `@capawesome/capacitor-app-update` the way `nativePurchase.ts` wraps RevenueCat (dynamic import behind `MODE === "mobile"`, the module namespace kept in the promise, never the plugin object; `nativeBundle.test.ts` fails if it reaches a web asset). `updateState(info, installedVersion)` is the pure verdict: `UPDATE_AVAILABLE` and a store version newer than the installed one (iOS compares `availableVersionName` with `currentVersionName`, Android `availableVersionCode` with `currentVersionCode`; Play never names the version, so the banner then says "A new version…"), with `immediate` = Play's `immediateUpdateAllowed` and `key` (name, else code) for the dismissal memory. `checkForUpdate()` asks the store at most once per app launch (answer cached in sessionStorage `crossword-clash:update-check`, a failed ask cached as "no update") and again when the app returns to the foreground after `RECHECK_AFTER_MS` (1 h); `dismissUpdate(key)` remembers "Later" per version in localStorage `crossword-clash:update-dismissed`. `useAppUpdate()` → `{ available, version, update, dismiss }` (available is false on the web, before the first answer, for the installed version and after Later); `openUpdate` runs `performImmediateUpdate()` on Android when allowed (OK or the player's cancel ends it, anything else opens the store page) and `openAppStore({ appId: IOS_APP_ID })` on iOS. `UpdateBanner` sits at the top of the menu, in flow (no safe-area padding of its own), tinted fill + icon, strings under `update.*`. Analytics: `app_update_shown` / `app_update_tapped` / `app_update_dismissed` with `version`. Needs no server side. Play's in-app update only works for a build installed from Play with the same package name and signing as the live release; a TestFlight build newer than the App Store build always reports "no update".
- **Safe areas in the apps**: the mobile build's viewport is `viewport-fit=cover` and `.native-app #root` (`index.css`) pads every `env(safe-area-inset-*)` once, so **in-flow page containers must not pad the insets themselves** (`MenuScreen` and `PageShell` once did, which put the menu's top bar a whole status bar too low in the app; on the web, where the viewport has no `viewport-fit`, those `env()` values are 0 and the browser keeps content clear of the notch). Fixed overlays (dialogs, toasts, the lockout banner) sit outside `#root`'s padding and do read the inset themselves.
- **Exit warnings**: `useBeforeUnload` hook adds browser-native "Leave site?" dialog during active multiplayer sessions (lobby + playing screens for both player and host/TV views). Prevents accidental tab closure during games.
- **Route transitions** (`src/routeModules.ts`, `src/lib/transitionNavigate.ts`, `src/lib/viewTransition.ts`, `src/lib/routeCommit.ts`, `src/layouts/SiteFrame.tsx`, `src/components/NavigationProgress.tsx`, `src/components/ui/TransitionLink.tsx`): every code-split screen's import lives once in `screenModules`; the route config and `prefetchRoute(path)` (longest-prefix match, once per route) share it, so a chunk warmed on intent (`TransitionLink`'s pointerenter/focus/touchstart, `prefetchOnIntent(path)` on buttons) is already there when the route's `lazy` asks. `navigateWithTransition` (hook `useTransitionNavigate`) cross-fades the root (160 ms, `index.css`; UA keyframes kept so the fade never dips) with `.vt-site-bar` held still and `.vt-brand` morphing (the menu wordmark → the SiteBar logo); the game grid is never named. It only starts a transition once the chunk is loaded (150 ms budget, else a plain navigate — the page is frozen on the old snapshot while the update runs, so never wrap a download), skips under reduced motion / without the API, and catches all three ViewTransition promises. **Two gotchas**: `navigate(to, { flushSync: true })` only commits synchronously with the `RouterProvider` from `react-router/dom` (`main.tsx`), and a route's *first* render still commits a few ms after `navigate` resolves, so the update also awaits `nextRouteCommit()`, signalled from `SiteFrame`'s layout effect. `SiteFrame` is a pathless route around everything (legal pages and `/host` included) and also holds `<ScrollRestoration />` (top on push, restore on back/forward; a no-op on the full-height game screens) and the pending bar (`useNavigation().state === "loading"` for 150 ms+, reduced-motion safe).
- **Internationalization**: i18next + react-i18next with English and Spanish translations in `src/i18n/`. Language detected from localStorage (`crossword-clash:language`) → `navigator.language` → `'en'`. `LanguageSwitcher` component on menu screens. `tStatic()` for non-React contexts (window.confirm, alert). `<Trans>` component for rich text with embedded links. Spanish uses `→`/`↓` arrows instead of Across/Down.
- **Routing**: React Router with `createBrowserRouter`. `IndexRedirect` and `HostIndexRedirect` components determine initial route based on context state, URL params, and localStorage. **`/` is the cold-start resolver only** (it resumes a saved room or solo game before showing the menu): every in-app link or `navigate` that means "the menu" goes to `/menu` (`SiteBar`'s default `backTo` and logo, the error screens, screens that have just cleared their own state), so "Back to menu" never lands back in a finished puzzle or a stale lobby. **Room session expiry** (`sessionPersistence.ts`): `MpSession.savedAt` is stamped on save, kept on a re-save of the same room, and renewed by `touchMpSession` while the player is in the room; `loadMpSession` ignores sessions over 12 h old, and `useRejoinEffect` refuses a still-`waiting` room unless the session was touched within the hour. **Finished state**: `completionModalDismissed` (GameContext) starts true for a solo puzzle restored already finished and is set before the modal navigates away; the play screens then show `FinishedBar` (time chip + Share re-opens the modal + Leaderboard for a daily) in the header. **Important**: `extractPuzzleFromUrl()` clears `window.location.hash` as a side effect, so `GameProvider`/`HostLayout` call it during `useState` init and store the result as `urlPuzzle`. Route redirects must check `urlPuzzle` from context, never `window.location.hash`. Deep-linked screens (lobby, spectate, play) redirect to the index route when puzzle is null (triggers rejoin flow).

Each manifest entry carries the puzzle's `puzzleIdentity()` so the screen can show solved/PB badges from local solo stats without parsing files. Four of the book's 50 are deliberately excluded (#21, #34 slurs; #40 Klan-joke pseudonym; #42 swastika grid). Pure helpers in `src/lib/classicLibrary.ts`; the import hub previews the 4 smallest and links to `/classics`. "Play solo" follows the daily-mini path (`handleSoloPuzzleLoaded` → `/solo/play`); "Race friends" follows the daily-race path (`setUrlPuzzle` → `/host-game/name`). `classicLibrary.test.ts` verifies the manifest against the files on disk. The `/classics` route's `lazy` loads the manifest together with the chunk (`prefetchClassicManifest` → module cache read by `knownClassicManifest`), so the screen paints its cards on its first frame instead of a loading line that then shifts.
- **Puzzle archive** (`/archive`, `ArchiveScreen`; spec and decision record in `docs/puzzle-archive-spec.md`): every published daily since the feed began (2026-10-16) as a month calendar with the viewer's own status per day, the selected day's puzzles beneath it with Play / Race, a resume row for the one solo game the device would resume, and a "solved · to catch up on" count. The list comes from a **generated** index — `public/daily-puzzles/index.json` (`{ first, last, months }`) plus `index/YYYY-MM.json` (one `DailyIndexEntry` per daily: day, slot, title, theme, author, size, clue count, `puzzleIdentity()` and the grid shape as `blocks`) — written by `pnpm build:daily-index` (`scripts/build-daily-index.mts`, run by `pnpm build`, `pnpm dev` and `pnpm daily:add`; committed like the classics' manifest, `dailyIndex.test.ts` fails if it drifts). It lives under `/daily-puzzles/` so the apps read it with the feed's CORS header and a missing month is a real 404. **The index files include future days** (so do the feed's static files): `publishedEntries`/`loadPublishedIndex` filter to `day <= today` on the client, and the screen never lists tomorrow. Status is derived, never stored (`src/lib/archive.ts`: `deriveArchiveItems` from `useBestTimes()` — local stats or the account's solves — plus every puzzle in **`src/lib/soloProgress.ts`**, the per-puzzle solo progress store: localStorage `crossword-clash:solo-progress`, one record per started-and-unfinished solo puzzle keyed by `puzzleIdentity()` with its typed cells, clock, `updatedAt`, filled/total counts; at most `MAX_PROGRESS_RECORDS` (30), oldest evicted; a record exists only once a letter is typed (`GameContext`'s solo save effect → `recordProgressCells`), the timer checkpoints its clock (`recordProgressElapsed`), `handleSoloPuzzleLoaded` hydrates it back (`HYDRATE_CELLS`) and `useSoloTimer` resumes its clock when the single timer record is another puzzle's, and it is deleted on finish and on Reset. `inProgressFrom` merges the store with the one legacy saved session (`crossword-clash-solo`, still what `/` resumes). Local-only for anonymous players and free accounts — `solves` stores finishes, not grids (spec §5.3); solved wins over in progress). **Plus accounts mirror the store** to the `solo_progress` table (migration `20261024100000_solo_progress.sql`: one row per user × `puzzle_key`, RLS select/insert/update need a real account **and** `has_entitlement(auth.uid(), 'plus')`, delete needs only the account so a lapsed subscriber can still drop a finished puzzle's row; `solo_progress_sweep()` deletes rows of users without Plus untouched for 90 days, its own pg_cron job at 04:27 UTC so `retention_sweep()` keeps one definition) through `src/lib/soloProgressSync.ts`: `soloProgress.ts` now emits change notifications (`subscribeProgressChanges`) after every write; `startProgressSync(userId)` upserts a changed record 2 s after its last change (at once on `visibilitychange` hidden and on stop) and deletes its row the moment it is cleared; `pullProgress(userId)` reads the rows and `mergeRemoteProgress` folds them in, newer `updatedAt` wins, without echoing to listeners. `AccountProvider` starts/stops the sync and pulls while `user && plus`, and again when the tab comes back. A refused write (RLS) is logged and the local record kept. Play goes `fetchDailyForDay` → `handleSoloPuzzleLoaded` → `/solo/play`, Race `setUrlPuzzle` → `/host-game/name`; past days post to no leaderboard (boards are today-only). The route's `lazy` warms the index with the chunk (`prefetchDailyIndex` → `knownPublishedIndex`), the menu links it from the solo list ("Past puzzles"), and `pageMetaFor` has its meta. **Gate** (`archiveWindowFor(viewer)` → a window in days or null, `isLockedDay(day, today, window)`): anonymous visitors play the last `ANONYMOUS_ARCHIVE_DAYS` (7, today included); once Plus is live (`plusEnabled()`) a free account plays `FREE_ACCOUNT_ARCHIVE_DAYS` (30) and Plus everything (spec §5.1 revision of 2026-10-24); before launch accounts see everything. Older days stay on the calendar with a lock glyph and their panel shows a benefit-led card instead of Play / Race: sign-in for anonymous (`openAccount({ placement: "archive" })`), "About Plus" for a free account (`openPaywall({ placement: "archive", feature: "archive" })`). - **Daily feed** (`src/lib/dailyFeed.ts`, `useDailyMini`/`useIsTodaysDaily` in `src/hooks/useDailyMini.ts`): a day's daily can be published as a static file, `public/daily-puzzles/YYYY-MM-DD.json` (local calendar day, transfer format plus optional `theme`), written by `pnpm daily:add <date> <puzzle file> ["Theme"]`. A day with a file uses it; every other day, and any fetch failure, falls back to the bundled rotation in `dailyMinis.ts`. The answer is cached per day in localStorage (`crossword-clash:daily-feed`; "no file" is re-checked after 3h) so `isTodaysDaily()` stays synchronous. The menu hero shows a placeholder until the first answer of the day. The native apps (mobile mode) read the same feed from `https://crosswordclash.com` — `/daily-puzzles/` is excluded from the SPA rewrite so a missing day is a real 404, and `vercel.json` sets `Access-Control-Allow-Origin: *` there because Vercel's automatic one is missing from 404s — so publishing a day reaches web and apps at once, with no app release. **Future days are gated by routing middleware**: the static files are committed weeks ahead and Vercel serves files before rewrites, so `proxy.ts` (root, `proxy.entrypoint` in vercel.json, matched to `/daily-puzzles/*` only) answers 404 for any day later than UTC date + 1 (the same rule as `daily_schedule`'s RLS) and lets everything else fall through; `proxy.test.ts` covers it. Dev and preview don't run it, so future days are visible locally. **Admin schedule**: a day with no static file is answered by `api/daily.ts` (vercel.json rewrites `/daily-puzzles/:day.json` there; Vercel serves real files first) from the Supabase `daily_schedule` table, whose RLS only exposes days that have started (≤ UTC date + 1). The constructor manages it from /studio through the `studio-schedule` edge function (STUDIO_TOKEN-gated, service-role writes). **Daily slots** (`DailySlot = "mini" | "midi" | "large"` in `dailyFeed.ts`): the midi (original 9×9s, `public/daily-puzzles/midi/`, `--slot midi`, rewrite to `api/daily.ts?slot=midi`, migration `20261018000000`) and the large are second and third dailies beside the mini; both have no fallback and no tile on a day with nothing published. `defaultSlotFor`: ≥ 11 wide → large, ≥ 8 → midi, else mini. The large is a second daily for original 15×15 themed puzzles. Static files live at `public/daily-puzzles/large/YYYY-MM-DD.json` (`pnpm daily:add --slot large …`), vercel.json rewrites `/daily-puzzles/large/:day.json` to `api/daily.ts?slot=large`, and `daily_schedule`/`daily_results` are keyed by `(day, slot)` (migration `20261017000000_daily_slots.sql`). The large has **no bundled fallback**: a day with nothing published has no large, and the menu shows no second tile (`useDailyPuzzle("large")` → `null`). Feed cache is per slot (`crossword-clash:daily-feed:large`). `todaysDailySlot()`/`useTodaysDailySlot()` say which daily a loaded puzzle is; each slot has its own leaderboard (`/daily/leaderboard` and `/daily/leaderboard/large`, `leaderboardPath()`), and the completion share caption names the slot. The studio's DailyQueue shows both queues and defaults the slot by grid size (`defaultSlotFor`: ≥ 11 wide → large).
- **SeedGrid construction engine** (`src/lib/seedgrid/`, CLI `pnpm seedgrid`): makes original puzzles the Ingrid way. The grid math is deterministic and browser-safe (so a future studio UI can reuse it): `dictionary.ts` (`WORD;SCORE;tags` lists, per-(position,letter) bitsets), `grid.ts`, `solver.ts` (`FillEngine`: arc consistency + MRV search, approvals per slot, global rejections, no dupes or shared runs longer than `maxShared` — 3 everywhere, engine-filled entries only; locked themers are the constructor's call — a one-step heatmap via `cellOptions()`), `layout.ts` (seed placement: same-length seeds paired in mirrored rows, one row between parallel seeds at minimum, `pairedPlacements`/`freePlacements` enumerate every pairing or crossing; `shapeSkeleton` adds blacks where the heatmap is worst), **grid standards** in `grid.ts` (`meetsGridStandards`: no 2×2 black block anywhere, corners white from 11×11 up — minis/midis need their corner blacks) that every skeleton builder enforces, `skeletonSearch.ts` (`enumerateSkeletons`: column-by-column construction with row pruning, the only way to shape stacked themers; `searchSkeleton`: annealing scored by the engine heatmap), `skeletonFinder.ts` (the studio's Lay out pipeline: random draws — `placement: "paired"` whenever `canPair` says the seeds mirror, so no long unthemed slot ever faces a themer; the free draw only for sets that cannot pair — → enumerated skeletons ranked by heatmap → annealing → lower score floors; reports the floor the layout fills at, which the studio surfaces), `audit.ts`, `ipuz.ts` (speed clues ride in an extension key). Claude only picks among proven-viable candidates, reviews the fill, and writes clues (`scripts/seedgrid/make.mts`, structured output via `claude.mts`; `claude-opus-5-5` by default). Word lists: `pnpm seedgrid:dict` builds the gitignored `base.dict` on the MIT Crossword Nexus Collaborative Word List's 0–100 scale (its catch-all 50 tier demoted to 47; numeral entries dropped; its long phrases are what make seeded midis fillable), with ENABLE + FrequencyWords filling in missing words. Frequency may only **lower** the score of single words (`scoring.ts`: rare ones cap at 45, below the usual 50 floor); phrases stored without spaces (GOATCHEESE) are naturally rare as tokens, so frequency never touches them, and `blocked.dict` from LDNOOBW; the committed `lively.dict` (Claude-proposed phrases, grow it with `pnpm seedgrid:lively`) and `rescore.dict` (hand overrides) layer on top. Spread the Word(list) is CC-BY-NC, so it is not used. **Two lists**: `base.dict` scores everyday words with FrequencyWords (CC-BY-SA data, private use only); `production.dict` uses only the Collaborative Word List (MIT), ENABLE (public domain) and SCOWL levels 10–70 (permissive; level 80 brings in UKACD) for commonness (`levelCap`/`levelScore` in `scoring.ts`). `pnpm seedgrid:studio-dict` writes both to `public/seedgrid/` plus `NOTICES.txt`. The studio loads `/seedgrid/words.dict` in dev and, in every other build, `words-production.dict` from the public `seedgrid` Supabase Storage bucket (`pnpm seedgrid:upload-dict` publishes it with NOTICES.txt; no deploy needed); `VITE_SEEDGRID_WORD_LIST` overrides both, and studio builds drop the private `words.dict` from their output unless it is named there. The CLI picks with `SEEDGRID_WORD_LIST=production`. Output lands in `artifacts/seedgrid/<date>-<slug>/` (`puzzle.ipuz` for `pnpm daily:add`, plus `review.md` with every curation/review decision). **Daily large** (`pnpm seedgrid:large`, `scripts/seedgrid/large.mts`): a themed 15×15 from a theme spec with no browser session — `--theme "Football x music" --seeds "touchdown under, goal post malone, …" [--title] [--allow-shared] [--min-score 50] [--seeds-floor 48] [--no-llm] [--dry-run]`, or `--batch docs/large-puzzle-themes.json [--only slug]` (any JSON/YAML list; the backlog's `entries[][0]` are the seeds) which continues past failures and writes a summary table. Pure helpers in `themedLarge.ts` (tested): `validateSeeds` (same-length pairs plus at most one centered odd entry; themers sharing a run longer than 3 are refused unless `--allow-shared`), `nestedEntries` (an engine entry of 4+ letters inside another entry is a duplicate; a contained entry no longer than `MAX_SHARED` is an allowed shared run, as in `audit.ts`) and `scoreFill` (quality = capped list scores, sub-tier entries charged double, partial-looking entries penalized unless the list scores them 60+, nesting penalized, `wordlists/theme-bonus/<slug>.dict` rewarded; a word from the committed `wordlists/ban.dict` throws the fill out and is also passed to the engine as a rejection — keep that list to junk, slurs and the genuinely crude; double-meaning words are ordinary fill). The CLI loads the Ingrid wasm engine in Node with the studio's `public/seedgrid/words-production.dict`, runs `findSkeleton` for `--layouts 2` skeletons (keeping the one whose tightest slot has the most options, then fewest flagged entries in quick fills, then quality per entry — a skeleton with a two-option slot dies on the first rejection there; at the floor it reports; `--seeds-floor` defaults to 48 because 47 is the list's demoted catch-all tier, and four stacked 13/14s need `--seeds-floor 45`), fills `--fills 24` times with a tightening pass (re-fill at the requested score everywhere but the slots that provably need the floor), shortlists 3 block-free fills, and Claude picks, rejects "must" entries (up to three refills, each pick the best fill so far that avoids every rejection, and a word the layout forces is kept and recorded for the editor; after the audit gate, local refills and swaps, the fill that ships gets a closing review whose leftover "must" entries are recorded for the editor); audit blocks (nested entries) are rejected and refilled the same way and fail the theme if they cannot be cleared; then each flagged entry gets a local refill (its crossings' ring, or the ring beyond, refilled at the requested score, kept when the fill scores better) and Claude may swap flagged entries for engine-listed alternatives that fit the crossings. Clues come from `cluesRequest` with the themers as question-mark puns and a content rule (nothing crude, sad or gross, no dialect mockery), then a Claude content review and a rewrite of what it flags. ## Game Modes

- **Solo**: Import puzzle → play locally → progress saved to localStorage only (per-puzzle in `soloProgress.ts`, plus the one resumable session); the server sees a `play_sessions` row, never a game.
- **Host Game (Player View)**: Import puzzle → enter display name → multiplayer game created with 6-char share code → lobby (with QR code for easy joining) → start when 2+ players joined. Host can close the room at any time from lobby or playing screen. Refreshing the page auto-rejoins.
- **TV / Host View** (`/host`): Read-only spectator display. Creates a game room without joining as a player. Shows grid, clue list with strikethrough for completed words, scoreboard, room code + QR. Host can start game when 2+ players join and close the room at any time. Per-clue speech announcements via Web Speech API or ElevenLabs TTS. Optional AI narrator mode provides snarky gameshow commentary (see AI Narrator section).
- **Join Game**: Enter share code or scan QR code → join lobby → play when host starts. Refreshing the page auto-rejoins (session persisted to localStorage).

## Multiplayer Input Flow

```
Keypress → useGridNavigation → wrappedInputLetter
  0. Lockout check: Date.now() < lockedUntil? → skip (letter input only; navigation still works)
  1. Local check: cell already filled? → skip
  2. Correct letter? → no: visual reject + apply lockout timeout (if configured)
  3. Optimistic: dispatch INPUT_LETTER with playerId
  4. Server: claimCellOnServer()
     → success: broadcast cell_claimed to others
     → fail: dispatch ROLLBACK_CELL
```

## Wrong Answer Timeout

Host configures a lockout penalty in the lobby before starting (Off, 1s, 2s, 3s, or 5s). Setting is broadcast to all players via `game_started` event payload. When a player enters a wrong letter, all letter input is blocked for the configured duration. A countdown overlay appears on the grid during lockout. Navigation (arrows, tab) still works. Solo mode is unaffected. Settings are defined in `src/lib/gameSettings.ts`, UI in `src/components/GameLobby/TimeoutSelector.tsx`, overlay in `src/components/LockoutOverlay.tsx`.

## AI Narrator (Multi-Backend)

TV/Host view supports an optional AI narrator that provides live gameshow commentary. The narrator is separate from per-clue TTS announcements — when a narrator is active, `speak()` becomes a no-op and the narrator handles all commentary.

### Narrator Backends

Three backends implement the `NarratorBackend` interface (`src/lib/narrator/types.ts`):

1. **ElevenLabs Agent** (`elevenlabs-agent`): ElevenLabs Conversational AI agent. Voice/personality configured in ElevenLabs dashboard. Edge function `agent-auth` returns signed WebSocket URL. Requires `ELEVENLABS_AGENT_ID` and `ELEVENLABS_API_KEY` env vars.
2. **OpenAI Realtime** (`openai-agent`): OpenAI Realtime API with GPT-4o. Built-in voice synthesis via WebSocket, PCM16 audio playback via `AudioContext`. Edge function `openai-agent-auth` creates ephemeral token. Requires `OPENAI_API_KEY` env var.
3. **Claude + TTS** (`claude`): Claude generates commentary text, then speaks via ElevenLabs TTS. Maintains conversation history client-side. Edge function `narrator-claude` proxies to Claude API with `claude-sonnet-5-5` (`NARRATOR_MODEL`; thinking at its lowest setting, `between_tools`, so the 256-token budget is all reply, and the text block is read by type), priced at list in `DEFAULT_NARRATOR_PRICING`. Requires `ANTHROPIC_API_KEY` env var.

### Settings

- `TTSEngine` (`"browser" | "elevenlabs"`) controls per-clue TTS voice when no narrator is active.
- `NarratorEngine` (`"elevenlabs-agent" | "openai-agent" | "claude" | null`) controls the AI narrator. `null` = no narrator (legacy per-clue announcements).
- Legacy `engine: "agent"` in localStorage auto-migrates to `narratorEngine: "elevenlabs-agent"`.
- Settings stored in `src/lib/ttsSettings.ts`, UI in `src/components/TTSControls/TTSControls.tsx`.

### Gating

No devtools localStorage gate — a regular visitor on `/host` can turn the narrator on from the TTS settings modal (shown whenever Supabase is configured, i.e. `isElevenLabsAvailable()`). Only available in TV/Host view (`/host` routes via `HostLayout`); never spawned for player or host-as-player views.

### Plus (per-user allowance) and the gate

With Plus live (`PLUS_GATES=1` Supabase secret, the server half of the client's `VITE_PLUS`), the four narrator functions run `_shared/plusAccess.ts` after the per-IP rate limit: `narratorGate(req, endpoint, minutes)` reads the caller from the bearer token (the client now sends the **session** user's access token, anonymous included, via `narratorHeaders()` in `src/lib/narrator/narratorAuth.ts`), and a Plus subscriber (`has_entitlement`) takes `minutes` from the 60-minute monthly allowance with `consume_allowance` (`agent-auth`/`openai-agent-auth`: `AGENT_GRANT_MINUTES` = 10 per grant; `narrator-claude`: one minute per `CLAUDE_CALLS_PER_MINUTE` = 6 calls, counted in `feature_usage` under `narrator_claude_calls`, via `chargeClaudeCall`; `tts`: 0, it rides the Claude path) → 402 `{ error: "allowance_exhausted", feature, used, limit, resetsAt }` when spent; anyone else gets only the demo (`demoOnly`: `?demo=1` on a demo-eligible endpoint within the per-IP grant limit) → otherwise 402 `{ error: "narrator_unavailable", reason: "plus" }`. The global cap stays as a backstop and grows with subscribers (`capWithSubscribers`: base + `PER_SUBSCRIBER_CAP_USD` 2 × active Plus rows, in both `narratorBudget` copies). Client: `narratorRefusal(res)` maps a 402 body to a sentinel (`narratorUnavailableSentinel`: `narrator_unavailable:budget` / `:plus` / `:allowance`); `useNarrator` exposes `pausedReason` ("budget" | "plus" | "allowance"; `budgetExhausted` is kept as `pausedReason === "budget"`), tries the one Claude-path demo for budget and plus (not allowance), never cascades on any of them; `HostSpectateScreen` shows `tts.narratorPlusRequired` / `tts.narratorAllowanceSpent` / `tts.narratorBudgetPaused`; the TTS settings modal shows a Plus note (`usePlusStatus`, which also drives the studio: it follows the session user and keeps the shared entitlement store loaded outside `AccountProvider`). Without `PLUS_GATES` every function behaves exactly as before.

### Cost control (owner budget cap)

- **Pure math**: `src/lib/narratorBudget.ts` (typechecked + unit-tested) prices `api_usage` ledger rows into a month-to-date USD estimate and an over/under-cap boolean. Mirrored for Deno in `supabase/functions/_shared/narratorBudget.ts` — keep the two in sync.
- **Server guard**: `supabase/functions/_shared/budgetGuard.ts` queries rolling month-to-date spend from the Neon `api_usage` table (via the existing `DASHBOARD_DATABASE_URL`) and, once estimated combined Anthropic+ElevenLabs+OpenAI spend reaches `NARRATOR_MONTHLY_USD_CAP` (default 20), refuses every narrator/TTS auth endpoint with HTTP 402 `{error:'narrator_unavailable', reason:'budget'}`. Fails open only when spend genuinely can't be measured.
- **Graceful client**: backends throw the `narrator_unavailable:budget` sentinel; `useNarrator` surfaces `budgetExhausted` (no cascade/retry loop) and `HostSpectateScreen` shows a friendly "taking a break" banner (`tts.narratorBudgetPaused`). Narrator stays off.
- **Demo allowance**: first-time TV hosts get a few sampled events (`src/lib/narratorDemo.ts`, metered in localStorage) on the cheapest Claude path even while over budget; the server independently caps demo grants per IP via the `narrator_usage` table.
- **Rate limiting**: per-IP via `_shared/rateLimit.ts` on all narrator auth endpoints. `narrator-claude` and `tts` share the same 60/h ceiling: the Claude narrator speaks every line through `tts`, so a lower voice limit would mute it mid-game.

### Session Lifecycle

`useNarrator` hook (`src/hooks/useNarrator.ts`) manages connection via `createNarratorBackend()` factory. Connection starts when game becomes active, stays alive through game completion so narrator can react to the winner. Auto-disconnects after 30s idle. Immediately disconnects on: room close, back to menu, new puzzle, engine change, mute, unmount, or `gameStatus → "waiting"`.

### Events

`GAME_STARTED` (puzzle metadata + player names), `CLUE_COMPLETED` (player, clue details, scores, remaining), `LEAD_CHANGE` (new/previous leader + scores), `GAME_COMPLETED` (winner + final scores). Event builders are pure functions in `src/lib/narrator/events.ts`.

### ElevenLabs Agent Specifics

- Mic muted via `setMicMuted(true)` — all input is text.
- **Idle chatter prevention**: Dashboard system prompt must include "NEVER ask if the user is still there. NEVER initiate conversation unprompted. Only speak when you receive a game event."
- **Speech interruption prevention**: Events arriving while agent is speaking use `sendContextualUpdate()` instead of `sendUserMessage()` to avoid cutting off the agent. When agent returns to listening, accumulated context is prompted with `sendUserMessage("Please comment on the recent events.")`.
